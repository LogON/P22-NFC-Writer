# Метка катушки Nelko P21 / Olympia P22: что показал Labelnise

*English version: [TAG_FORMAT.md](TAG_FORMAT.md)*

Формат восстановлен по декомпилированному Labelnise (jadx 1.5.1) и серверному API приложения.
Каталог этикеток выгружен с сервера приложения в `tools/catalog_P21_P22.json` (56 записей). 55 записей для P22 лежат в приложении: `app/src/main/assets/labels.json`.

## Главное

1. **Шифрования и подписи нет.** Метка — NTAG203/213, полезные данные открытым текстом лежат в страницах 4..7.
   `libencryption.so` / `READ_DECRYPTION` нужны только картриджам струйных Pocket-принтеров.
2. **Метку читает принтер.** Приложение шлёт по BLE `1B 21 6F 0D 0A`. Принтер отвечает 16 байтами:
   `[статус] [0C] [12 байт стр. 5..7] [CRC16/MODBUS, big-endian]`. CRC считает принтер.
3. **Оформление, размеры и фон этикетки приложение берёт не из байтов, а из серверного каталога.**
   Эти 12 байт в hex служат *кодом*. Приложение делает запрос
   `GET https://app.labelnize.com/api/label/getLabelByCode/<код>` (авторизация не нужна) и получает шаблон:
   имя, ширину и длину, gap, картинку-фон (`bg`, это и есть «декор»), тип.
   Разбирать байты само приложение (`ConsumablesPaperBean.parse`) начинает, **только если кода нет в каталоге**
   или нет сети (тогда сначала проверяется локальная БД `LabelPaperDB`).
   Отсюда и результаты перебора: любой код вне каталога даёт «Новую этикетку» с размерами из локального разбора,
   а у него свои особенности (см. ниже). Код, случайно совпавший с другой записью каталога, даёт размеры этой записи.
4. Без распознанной метки приложение только предупреждает («Не удаётся распознать оригинальную бумагу…»)
   и разрешает продолжить. Разрешение оно не меняет, значит, ограничение — в прошивке принтера.

## Что значат байты (по каталогу и по коду parse)

Код = `k0 k1 k2 k3 k4 k5 k6 k7 k8 k9 k10 k11` = страницы 5..7.

| k | поле | что видно в каталоге |
|---|---|---|
| 0 | — | всегда `01` |
| 1 | формат | `12` — 14 мм с промежутком; `02` — 12 и 15 мм (старый формат); `22` — лента и кабельные |
| 2 | **номер дизайна/цвета** | `02` прозрачный, `03` белый, `04`/`05`/`06` розовый/синий/жёлтый (GAP03/05/04), `09`…`46` — декоративные GAP06…GAP43. Значения идут как BCD (`09, 10, 11…19, 20…`, а `0A`–`0F` пропущены) |
| 3–4 | партия | всегда `00 03` |
| 5 | тип | `01` — с промежутком, `00` — лента |
| 6 | gap | `12` у этикеток, `00` у ленты, `05` у кабельной |
| 7 | — | всегда `12` |
| 8 | — | всегда `15` |
| 9 | длина, мм | `1E`=30, `28`=40, `32`=50, `4B`=75, `0A`=лента |
| 10 | ширина (формат `02`) | `0C`=12, `0F`=15; в остальных форматах `0F` |
| 11 | ширина (форматы `12`/`22`) | `0E`=14, `0C`=12 (лента); в формате `02` всегда `0F` |

**Почему сбивалась ширина.** Для 12 и 15 мм каталог использует формат `k1=02`: ширина лежит в **k10**, а k11 = `0F`.
Для 14 мм формат `12`: ширина в **k11**, а k10 = `0F`. Если поменять ширину «не в том» байте или сменить k1,
приложение прочитает 15 мм вместо 14 и т.п.

**Почему не менялся цвет.** Цвет и декор задаёт только k2, причём это номер записи каталога, а не цвет.
Например, `01 12 22 …` — это GAP42, а не какой-то «цвет 0x22». При локальном разборе (кода нет в каталоге)
приложение знает только значения 2..8, всё остальное показывает белым.

**Кабельные этикетки.** Для P22 в каталоге их нет: у всех записей `isCable=0`. Единственная похожая — `14x75+47mm`
(код `0122470003010512154B0F0E`, флажок с хвостом 47 мм), но она числится только за P31S/P21.
Приложение Labelnise считает этикетку кабельной, если в формате `0x22`/`0x3x` старшая тетрада k5 равна 5–8
(направление хвоста: 5 вверх, 6 вправо, 7 вниз, 8 влево). Ни одна известная катушка так не закодирована.

**Превью.** У каждой записи каталога есть поле `image`: ссылка на картинку рулона на `oss.nelko.net`
(цвет, декор, форма). Приложение подтягивает их с сервера в рантайме и кеширует; сами изображения
Nelko в этом репозитории не хранятся.

**Формы.** Сейчас в каталоге для P21/P22 нет ни одной некруглой/фигурной этикетки с RFID-кодом.
`getLabelPaperShapeList` отдаёт только `Circle`. Фигурные декоры из каталога — это прямоугольники 14x40 с фоновой картинкой
(`hasBg=1`). Форма выреза определяется самой бумагой, метка её не задаёт.

## Серверное API (`https://app.labelnize.com/api`)

Без авторизации работает. JSON-POST там, где он нужен (form-urlencoded сервер не принимает).

| Эндпоинт | Что даёт |
|---|---|
| `GET /label/getLabelByCode/{код}` | шаблон по коду метки |
| `POST /label/getLabelList` `{"pageNo":1,"pageSize":1000,"dev":"P22"}` | весь каталог с кодами → `tools/catalog_P21_P22.json` |
| `GET /label/getTypeList/P22` | категории: 12x40, 14x30, 14x40, 14x50, 14x75, 15x40, Continuous |
| `GET /templateVip/getDeviceList` | конфиг моделей: dpi, размеры, типы бумаги |

Пустые для P21/P22: `getLabelPaperSetList`, справочник неисправностей `qa/getTroubleRemovalList`.
Всё остальное — аккаунт, шаблоны, AI-картинки, подписки; к меткам отношения не имеет.

### Конфиг P22 с сервера (`getDeviceList`)

* `dpi: 203`, `maxWidth: 12` — печатная полоса 12 мм ≈ 96 точек при любой ширине ленты.
* `paperType: "0,1,2"` (лента, с промежутком, blank), `paperMinLength: 10`, `paperMaxLength: 1000`
  (у P21 максимум 75).
* `printingHeightList` — реальная печатная длина: 30→25, 40→34.5, 50→44.5, 75→69.5 мм
  (у P21 40→35.5). Это отступы по 2.75 мм с каждой стороны: рисунок длиннее этого приложение обрезает.
* `isEncrypt: 1` — для P22 приложение запрашивает метку у принтера (`isPaperEncrypt`). Само по себе это не шифрование,
  а просто флаг «модель с RFID».
* `printingNonPaperNotify: 0` — предупреждение о неоригинальной бумаге для P22 выключено, печать идёт без вопросов.
* `rfidProtocol: 1`, `paperCode: 011203000301121215280F0E` — бумага по умолчанию 14x40 White.

## Как получить нужную этикетку

Берите код **готовой записи каталога**, не собирайте байты вручную:

```
python tools/make_tag.py --catalog GAP22 -o gap22.nfc
python tools/make_tag.py --catalog "15x40mm GAP White" -o w15.nfc
python tools/make_tag.py --code 010204000301121215280C0F --pages      # 12x40 розовая
python tools/make_tag.py --width 14 --length 75 --color white -o w14x75.nfc
```

Без `--code` и `--catalog` скрипт выбирает формат по ширине сам (12/15 → `02`, 14 → `12`). Все проверенные комбинации
попадают точно в записи каталога, а `--color blue` с UID синей катушки побайтно совпадает с `docs/dumps/012.nfc`.

Проверено:
* метки, записанные кодами из каталога, принтер распознаёт, и они работают как нужно;
* декоративные катушки (GAPxx) тоже работают: приложение подгружает нужный декор из каталога.

Что не проверено:
* что проверяет прошивка, когда снижает разрешение. Самый надёжный вариант — коды из каталога: это
  ровно те значения, которые прошивка видит на настоящих катушках.
